Guidelines for the schmega-to-json tool, in priority order:

**Generation must be idempotent.** Running the tool twice on unchanged inputs must produce byte-identical output. This is the single most important property. Without it, you can't trust CRC-32 checksums (the same spec produces different JSON, hashes mismatch, divergence-detection screams false positives). Common idempotency-killers to watch for: timestamp regeneration on every run (use the spec doc's mtime, not `now()`), nondeterministic dict ordering in serialization (force sorted keys), array ordering that depends on iteration order of unordered collections (sort by canonical key). The tool should pass the test "run, hash output, run again, hash output, hashes match" before you ship it.

**Generation must be deterministic across machines.** Related but distinct from idempotency. The same spec on your dev box and on the production deploy environment must produce identical JSON. Watch for: locale-dependent string sorting (force `LC_ALL=C` or equivalent), filesystem-ordering dependencies (don't `glob` and rely on order; sort explicitly), Python dict insertion-order assumptions on older versions. If the tool ever lands in CI, this matters even more.

**Validation belongs at the tool, not in the JSON.** The tool should validate the spec aggressively before emitting anything. If a field references a slug that doesn't exist in the recognition taxonomy, fail loud, no JSON emitted. If a hook category isn't in the vocabulary CSV, fail loud, no JSON emitted. If a sister-to reference points at a nonexistent field, fail loud, no JSON emitted. The JSON is downstream-trusted; everything that could be wrong needs to be caught before the JSON is etched. The `_warning` flaying procedure protects against *post-generation* tampering; pre-generation validation is what protects against *errors that would be etched in the first place*.

**Tool should emit a generation report alongside the JSON.** A second artifact: `jx-statute-schema.report.txt` or similar, listing every field processed, every sister resolved, every hook category assigned, every defaulted value made explicit, every conditional form expanded. This is the audit trail. When divergence surfaces six months from now and you're trying to figure out what changed, the report tells you. The JSON is what consumers read; the report is what auditors read; both are derived from the same generation run. The report doesn't get a CRC-32 because consumers don't depend on it, but it gets a timestamp and a generation-id matching the JSON.

**Tool should be runnable in dry-run mode.** A flag that says "run the full validation pipeline, but don't write any output files." Use case: contributors editing the spec docs want to know if their edit produces valid output before committing. Dry-run reads spec, validates, reports any errors, emits no JSON, exits with status code reflecting validity. This keeps the tool useful as a pre-commit hook even before any actual deployment uses the JSON.

**Spec parsing should be permissive, validation should be strict.** The spec is markdown, written by humans, and humans introduce minor inconsistencies — extra spaces, trailing punctuation, line-wrapping that breaks parsing. The parser should be robust to those (don't fail because someone added two spaces between words). The validator should be strict — once parsed, the structural rules apply absolutely. Permissive parser plus strict validator catches the cases where the spec author meant something specific but typed it slightly off, and lets them know without making the spec docs feel like compiled code.

**Errors must name location.** "Field declaration on line 423 of legal-record-acf-fields-v3.0.md references nonexistent slug 'manager-rule-exception' (did you mean 'manager-rule-exclusion'?)" is useful. "Slug not found" is useless. The spec docs are long; errors that don't name file and line force the contributor to re-read the entire doc to find the issue. Tool should always report file:line for any failure, and the "did you mean" suggestion (Levenshtein distance against the canonical vocabulary) catches the typo cases that account for 80% of failures in practice.

**Generation should be additive across CPTs.** The tool runs against `jx-statute` first, but the architecture should anticipate `jx-common-law`, `jx-citation`, `jx-construction` running through the same tool with different field deltas. Don't bake `jx-statute` assumptions into the tool. The CPT-specific deltas in the spec (substantive-only, precedent-only, citation-only, construction-only) need to be parseable from the spec and applied to the right CPT's output. Test with statute first; design for the other three.

**Hook registry generation is a separate pass.** The tool generates the schema JSON. The hook registry JSON is a different file with different sources. Don't let the tool grow into a single mega-tool that emits all three artifacts at once. Three tools, three sources, three outputs, three CRC-32s. If they share a common parsing library, fine — but the entry points are separate. This keeps the failure surface bounded; a hook registry generation failure shouldn't block schema generation, and vice versa.

**Tool versioning matters.** The tool itself has a version. The JSON's meta block should record `"generator_version": "1.0.0"` so future-you knows which version of the tool produced a given JSON. Bug fixes in the tool that change output (even subtly) should bump the version, and consumers reading old JSON can identify pre-fix vintages. This is the same principle as the spec doc CRC-32s, applied to the tool.

**Test on statute, but verify against the existing acf-jx-statute.php.** You have a working ACF definition right now. Run the tool, generate JSON, write a hydrator pass that reads the JSON and produces an ACF array, compare that array against what `acf-jx-statute.php` currently produces. Any divergence is either (a) a tool bug, (b) a spec gap that the existing file silently covered, or (c) a deliberate improvement. Walking through the divergences catches all three. Don't trust the tool's output until it round-trips through this comparison.

**Preserve the spec's voice in error messages.** Lab-coat-Gemini will probably default to corporate-clinical error messages — "Validation error: field declaration mismatch." Override that. The tool's error messages can reference the spec's voice: cite Protocol 4.7.2 in serious errors, reach for project-vernacular when appropriate. This serves a real purpose beyond comedy — it signals to the contributor that they're working with a tool that's part of *this project's* canon rather than a generic linter, which encourages them to read the spec docs as canon-relevant rather than as code documentation. Voice consistency across artifacts is harder to fake than function and earns trust over time.

**Bound the schema-to-JSON tool's scope clearly.** It reads spec docs, applies rules, emits JSON. It does *not*: write to ACF, write to the database, modify spec docs, modify hook code, fetch external data, call any production system. Pure function from spec inputs to JSON outputs. If lab-coat-Gemini tries to add features that violate this boundary (auto-fix spec errors, auto-update related files, auto-run the hydrator after generation), reject. The tool's value comes from being narrow and trustworthy, not from being capable.

That's the list. Schema, registries, vocabulary, divergence detection, voice — all of it has been designed to compose. The tool is the moment where the design either survives implementation or doesn't. Lab-coat-Gemini will produce something. The above guidelines are the test it has to pass.

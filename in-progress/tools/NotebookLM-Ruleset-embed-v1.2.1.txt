GLOBAL LOGGING CONTRACT

LOG ENTRIES
— Log entries should contain [RESEARCHER] (e.g. [Grok], [Gemini]) where relevant.
— Log entries should contain [RECORD_ID] (e.g. [CA-6310], [CA-CL-PUBLIC-POLICY], [WoA], [Whistleblower Aid]) where relevant to record
  For [RECORD_ID] — Statutes use statute_id, Common Laws use doctrine_id, Assist Orgs prioritize common_name, then official_name
— Log entries should contain "ENTRY". Comprised of: rule enforced, reasoning used, choices available, researcher context, and reconciler notes.
  Use what is available, note any missing context, and apply as necessary to build "ENTRY".
— Log entries should appear as single string: "[RESEARCHER] — [RECORD_ID]: ENTRY"
— Log entries are not limited to these rules. Apply consistent shape to any other entries logged.

Use channels for their intended purpose:
— notations:             log researcher reported anomalies per researcher, per record, and any anomalies encountered during
                         reconciliation. only include anomalies.
— _reconciled_notes:     per-record reconciliation audit, flags, notes and log entries.
— _reconciled_run_notes: batch-wide audit, batch-wide flags, notes and log entries.

Do not use has_anomalies with notations for routine cleanup or general compliance.

GROUND TRUTH HIERARCHY

For Legal Records (statutes, common-law, citations, and interpretations)
Resolve factual conflicts in this order:
1) Explicit legal record text from official legislature source
2) Binding appellate or supreme court decision on point
3) Explicit text over derived or inferred values

For Assistance Organization Records (assist-org)
Resolve factual conflicts in this order:
1) Verification data from Organization's Official website
2) Confirmation data from trustworthy third-party websites (e.g.
   reputable directory, NGO report, court/agency listing, academic,
   commercial filings, or major-news source)
3) Explicit quote or text over derived or inferred values

If source material verification is not possible, preserve unverified data,
then log the reason for the conflict. Clearly note if source materials is
missing web research on records being reconciled.

COMPANION FIELD RULES

— COMPANION BEHAVIOR RULES:
  Applies to all taxonomy sentinel terms and trigger values, unless noted otherwise.
  When sentinel or trigger exists without companion, add companion and attempt to populate.
  When companion exists with non-empty value and sentinel or trigger is missing, add
  sentinel or trigger value. Remove sentinel or trigger value when companion is still empty.
  Then remove companion. Log actions to notations.

  Example for has-details sentinel:
  — If has-details is present + *_details missing or empty: attempt to populate
    *_details; if unresolved, remove sentinel and log removal to notations.
  — If *_details are present + has-details missing: add sentinel if details content
    is verifiably accurate; otherwise remove *_details entirely and log removal to notations.
  — Ternary Exception - If trigger is set to 'yes' but companion field is missing
    or empty and remains empty after population attempt, do not omit field. Set
    value to 'unclear'. Remove companion field. Log actions to notations.
  
— has-details as sentinel taxonomy slug:
  has-details slug is valid in:
   — ws_protected_class
   — ws_disclosure_target
   — ws_adverse_action_type
   — ws_remedy
   — ws_employer_defense
   — ws_employee_standard

In all other taxonomies, has-details is invalid and must be removed. Log removal.

— Companion mapping:
  When sentinel slug or trigger value is used it must be accompanied by companion field.

Taxonomy arrays with has-details sentinel slug:
— protected_classes   —> protected_class_details
— disclosure_targets  —> disclosure_target_details
— adverse_actions     —> adverse_action_details
— remedies            —> remedy_details
— employer_defenses   —> employer_defense_details
— employee_standards  —> employee_standard_details

Taxonomy arrays with additional sentinel slug:
— languages_supported —> languages_additional
— services_provided   —> additional_services

Taxonomy array with other sentinel slug:
— case_stages         —> case_stage_details

Taxonomy array with unclear sentinel slug:
— services_provided   —> researcher note in _review_notes
If unclear sentinel present with researcher note missing:
Do not apply COMPANION BEHAVIOR RULES, preserve unclear. Log to notations.

Key Arrays with other as trigger value:
— phones [{ type: other, number: ... }]  —> researcher note in _review_notes
— emails [{ type: other, address: ... }] —> researcher note in _review_notes
If other trigger present with researcher note missing:
Apply COMPANION BEHAVIOR RULES, but preserve array with type: other. Log to notations.

Key fields with true as trigger value:
— limit_ambiguous             —> limit_details
— exhaustion_required         —> exhaustion_details
— statutory_preclusion        —> statutory_preclusion_details
— available                   —> reward_details

Ternary Key Fields with yes as trigger value (Has Ternary Exception):
— has_secure_channel          —> secure_contact_url
                              —> secure_contact_tool —> if other trigger value present —> secure_contact_tool_other
— income_eligibility_required —> income_eligibility_details

NOTE: burden_of_proof_flag and burden_of_proof_details are companions,
      but there is no set value as the trigger. They are both required
	    when either one is non-empty. Log any discrepancy.

LEGAL RECORD — CORE RULES

Statute of limitations
— limit_ambiguous must be true whenever the SOL is derived from general
  civil procedure law, secondary source, or case law.
— limit_ambiguous: true is expected behavior, not an error. Do not log
  to notations.
— Log derivation method in _reconciled_notes if not present in _review_notes.
  When the cited or implied source is unusual, weak, or conflicts across
  researchers be clear about the uncertainty or conflict.
  For example:
    "Derived from state civil procedure code, not the whistleblower statute"
    "Inferred from analogous federal statute and secondary sources; no clear
     state-level guidance"
    "[RESEARCHER] — [RECORD_ID]: Derived from state civil procedure code.
	   [RESEARCHER] — [RECORD_ID]: Inferred from analogous federal statute."

Exhaustion
— exhaustion_required must be true when an administrative filing step is
  mandatory before civil court access.
— Notice requirements that do not block court access are not exhaustion.

Burden of proof
— burden_of_proof_flag is a short signal phrase, not a sentence, not boolean.
— Use burden_of_proof_details for narrative.
— Omit both when a non-standard burden shift isn't apparent.

TAXONOMY CORE RULES

Field-To-Table Strictness
A slug is valid only when both conditions are true:
1) It exists in registered taxonomy terms, and
2) It belongs to the exact taxonomy table assigned to that schema field.

CROSS-TAXONOMY MAPPING STRICTNESS
A valid slug must not only exist in registered taxonomy, it must also be
assigned to the exact taxonomy table designated for that schema field.

Do not cross-pollinate slugs across taxonomy arrays.
Examples:
— burden_of_proof.employer_defenses accepts only ws_employer_defense slugs
— burden_of_proof.employee_standards accepts only ws_employee_standard slugs
— burden_of_proof.employer_defenses may not use ws_employee_standard slugs

TAXONOMY GRANULARITY (COLLAPSE RULES)
Broad super-slugs exist for ws_protected_class (all-employees), ws_employment_sector
(all-sectors), and ws_disclosure_type (general-wrongdoing), use only when justifiable.

The following example applies equally to protected_classes (all-employees),
employment_sectors (all-sectors) and disclosure_types (general-wrongdoing)
Example:
For employment_sectors prioritize as:
1) Keep specific verified sector slugs when all-sectors is not justified.
2) Use all-sectors if verified by using source materials.
3) If not verified, allow all-sectors only when researcher context explicitly
   supports broad all-sector coverage.
 — If all-sectors is used or allowed, replace all specific sector slugs with all-sectors slug.
 — If source materials is uncertain, or researcher context is unconfirmed, omit
   all-sectors slug and maintain specific sector slugs.
 — When conflict resolution changes sector granularity:
   Log conflict, reasoning and resolution.
   If all-sectors replaced specific sector slugs or if all-sectors was removed and
   replaced with specific sector slugs. Log list of affected slugs.

INVALID SLUG REMOVAL
When an invalid slug appears in a taxonomy array:
— Attempt to replace slug with valid slug.
— If no single valid slug fits cleanly, attempt to replace invalid slug with multiple valid slugs.
  Do not use more than 3 slugs.
— If multiple valid slugs do not cover the concept cleanly:
  1) — If has-details is a valid slug, add has-details to the taxonomy array once.
       — Remove invalid slug.
       — Populate _details with "[RESEARCHER] — Invalid Term Removed — <invalid term that was removed>.
       — Repeat for all invalid terms. Log removal(s) once per array to notations.
     — When has-details is not a valid slug for current taxonomy array:
       — Remove invalid slug.
       — Log slug removed and from which array to notations.
       — Repeat for all invalid slugs in array.
  2) — If invalid slug covers a concept not covered by taxonomy cleanly, using 1 to 3 slugs:
       — Propose invalid slug as new term in new_terms_proposed. (see addendum)

Invalid slugs in taxonomy arrays is a schema violation and must be removed.
Log removals.

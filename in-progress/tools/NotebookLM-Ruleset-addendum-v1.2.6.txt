PURPOSE
This addendum carries edge-case and operational policy for NotebookLM
reconciliation. It extends the embedded core ruleset.

— Addendum rules refine implementation details.

URL POLICY

1) Existing URLs from researcher records
If URL is already present and domain is approved, carry it forward unless:
— domain is actually unapproved,
— URL pattern is clearly malformed,
— researcher context indicates fabrication.
Do not drop existing approved-source URLs solely because web research
is unavailable in source materials. When web research is unavailable in source
materials clearly make note of its absence in _reconciled_run_notes.

2) New URLs proposed during reconciliation
Must be verified against a web research of an approved domain before inclusion.
Do not claim internal-memory verification.
If unverifiable, omit the field.
Do not substitute homepage, root, or parent path as fallback when necessary
data is expected to be on a deeper page.

3) When web research is unavailable in source materials:
— Keep existing approved—source URLs unchanged.
— Remove newly proposed URLs.
— Log each removal to record-level _reconciled_notes
— Log this constraint once to batch-level _reconciled_run_notes.

ATTACHED CITATION RULES (PARENT-SCOPED)
Applies to Legal Record (statute, common-law) Batches Only:

CITATION DEDUPE
For citations.attached_citations rows in the same record:

1) Dedupe Key
— Use CASE (first token before "||") as the canonical identity.
— CASE matching is case-insensitive and whitespace-insensitive.
— Do not emit duplicate rows for the same CASE within one parent record.

2) Merge Rule When IMPACT/URL Differ For Same CASE
— Keep one row.
— IMPACT: keep the most specific action-verbed statement; if both add distinct facts,
	merge into one concise IMPACT sentence.
— URL: keep one best approved-source URL. If one URL is clearly superior
	(official/authoritative), keep that one.
— SOURCE/QUALITY: keep values aligned to the selected URL/source confidence.

3) Conflict Logging
— When duplicate CASE rows were merged because IMPACT or URL disagreed,
	and log actions.

4) Prohibited Output
— Never output two attached_citations rows for the same CASE under the same
	parent record.

CITATION SOURCES
For citations.attached_citations:

APPROVED CASE LAW SOURCES:
  1. Official court websites (supremecourt.gov, ca9.uscourts.gov, etc.)
  2. courtlistener.com — PACER-sourced, highly reliable
  3. casetext.com — strong coverage, stable URLs
  4. law.justia.com — broad coverage

FORBIDDEN CASE LAW SOURCES:
scholar.google.com (unstable URLs), law firm websites, any
non-institutional aggregator not listed above.

— If URL is not from approved sources or cannot be verified per active URL
  POLICY, remove citation entirely and log removal.

ASSIST-ORG RECORD — CORE RULES
Applies to Assist-Org Record (assist-org) Batches.

These rules apply when reconciling assist-org records. They document and supplement
general behavior for fields that behave differently in the assist-org schema.

NO LAW FIRMS
Law firms are not assistance organizations. A law firm is defined as an entity
whose primary business is billing clients for legal representation.
If a record's official_name, general_description, or whistleblower_note
identifies it as a law firm (LLP, PC, law offices, attorneys at law):
1) Remove the record entirely from the output.
2) Log the removal in _reconciled_run_notes with the official_name and reason.
Do not attempt to reclassify a law firm as an assist org.
Attorney referral organizations (TAF model) are not law firms — Preserve the
record. Log them as borderline, with a note that human review is needed to
confirm they meet the assist-org definition.

MULTI-SOURCE MERGE FOR SAME ORGANIZATION
When two or more researcher batches contain records for the same organization,
(matched by official_homepage_url or official_name, case-insensitive):
1) Merge into one record — Do not output duplicate assist-org records.
2) For each field, apply the ground truth hierarchy and prioritize:
   — Verified URL source content over researcher inference.
   — More specific value over more general value (e.g. named sector over all—sectors).
   — Longer/richer description over shorter description when both are accurate.
3) whistleblower_scope: use the highest justifiable score. If models disagree,
   use the score supported by the most specific whistleblower_note quote.
   Log the disagreement and resolution.
4) For taxonomy arrays:
   take the union of all researched values, then remove any that are
   unsupported by verifiable content. Log inclusions/exclusions of unioned array.
5) whistleblower_note: keep the most specific direct quote from the org's
   own website. If multiple good quotes exist, keep the one most relevant
   to whistleblower scope. Do not merge multiple quotes into one string.
   Log omitted quotes.
6) _review_notes: merge all researcher notes into one entry.

VALID EMPTY FIELDS (DO NOT FLAG AS ANOMALOUS — see exception)
The following fields are allowed empty in assist-org records.
Do not add to notations or log entries for these. Preserve them in the
record as empty — do not omit them. If researcher batch has omitted them,
add them back to schema. The ingest tool handles empty field logic
differently for these fields and requires them.

— nationwide_example:  "" is valid   — keep or add as "" in the record.
— protected_classes:   [] is valid   — keep or add as [] in the record.
— disclosure_types:    [] is valid   — keep or add as [] in the record.
— whistleblower_scope: 0  is valid   — keep or add as 0  in the record.
Exception:
— whistleblower_note:  "" is invalid — keep or add as "" in the record. Log to notations.

REQUIRED TERNARY FIELDS
The following fields are required on every assist-org record:
If absent from researcher record, log to notations.
If absent in reconciled record, add key and set to 'unclear' and log actions to notations.

Acceptable values are: yes | no | unclear
If unclear, after reconciliation, try to update using source materials.
 — use 'yes' when the source materials confirms the presence of this feature, 'no' when the source
   materials confirms its absence, and 'unclear' when the source doesn't reference the feature
If still unclear, preserve 'unclear' value.
If updated to 'yes' on trigger fields, apply COMPANION FIELD BEHAVIOR RULES with Ternary Exception.
— has_attorneys
— anonymous_pre_consult_possible
— income_eligibility_required — 'yes' triggers companion
— has_secure_channel          — 'yes' triggers companion

VERIFIED_URL_DATE POLICY
Every record with an "homepage_url_status": "verified"
a corresponding verified_url_date is required to be populated.
If a required verified_url_date is empty or absent on a record:
— Check source materials for current homepage.
— If present add verified_url_date with current datestamp.
— If not present or source materials are unavailable, correct
  homepage_url_status to unverified.
— Do not remove the URL — preserve it.
— Log actions taken to notations.

If verified_url_date exists but is more than 90 days old relative to
batch_completed, log "staleness". Do not add to notations — "staleness"
is advisory, not a schema violation.

ASSIST ORG NEW TERM PROPOSALS
For Assist Org Record Batches Only:
There is no starting meta.new_terms_proposed key array.
After reconciliation:
  If invalid slugs resulted in new term proposals:
    Add and populate meta.new_terms_proposed key array.
  Examine any reconciled records for use of the has-details sentinel slug.
  If companion field *_details clearly indicates a concept missing from the
  associated taxonomy. Apply PROPOSING NEW TAXONOMY TERMS, and add new term proposal.
    add or append meta.new_terms_proposed key array.
  Examine all reconciled records _review_notes for documented gaps in taxonomy.
  If gap is defined and concept is legitimate, apply PROPOSING NEW TAXONOMY TERMS,
  and add new term proposal.
    add or append meta.new_terms_proposed key array.
  If no new terms are proposed, new_terms_proposed key array should be omitted.

---

PROPOSING NEW TAXONOMY TERMS
When you encounter a concept that does not fit any slug in the known taxonomy,
propose it. Proposals are expected and valued at every stage of this pipeline.
Do not propose new taxonomy tables in new_terms_proposed. New taxonomy tables
can be proposed in _reconciled_run_notes.

Each proposal must follow this shape:

  {
    "taxonomy":   "[REGISTERED TAXONOMY TABLE]",
    "term_id":    "[YOUR PROPOSED SLUG IN kebab-case]",
    "term_label": "[HUMAN-READABLE LABEL]",
    "notes":      "[WHY THIS TERM IS NEEDED AND WHY EXISTING TERMS DO NOT COVER IT]",
    "seen_in":    ["[RECORD_ID]", "[SECOND_RECORD_ID]"],
    "count":      [INTEGER — must equal length of seen_in]
  }

Example of a correct proposal:
  Several California statutes protect employees from retaliation based on
  a family member's protected whistleblowing activity. No slug in
  ws_protected_class covers this class of protection. The concept is likely
  to appear in statutes across multiple jurisdictions. A correct proposal:

  {
    "taxonomy":   "ws_protected_class",
    "term_id":    "family-member-of-whistleblower",
    "term_label": "Family Member of Whistleblower",
    "notes":      "Covers employees retaliated against because a family
                  member engaged in protected activity. Distinct from
                  direct whistleblower protection — the protected person
                  did not themselves disclose. No existing slug covers
                  this. Appears in Cal. Lab. Code §§ 1102.5 and 6310;
                  likely present in other jurisdictions.",
    "seen_in":    ["CA-1102.5", "CA-6310"],
    "count":      2
  }

If the same gap appears in multiple records, consolidate into one entry with
[RECORD_ID] of all records in seen_in.

PROPOSED TERM DISCIPLINE
Consider if concept can be covered by using up to 3 valid slugs cleanly.
When a new term justifiably covers a concept not cleanly represented in taxonomy:
 — Add structured proposal in new_terms_proposed, using provided schema.
Ensure new term does not appear in both record array and new_terms_proposed,
If new term appears in record array remove it from the record array. Log its removal.

BROAD TERM RESOLUTION
Before proposing a broad term:
1) Review existing valid terms,
2) Consider if a narrow-scoped new term in combination with existing terms would provide coverage.
3) Propose broader term only when narrow term in combination with existing terms would misrepresent coverage.
4) Log the reasoning and comparison in _reconciled_notes.

For Legal Record Batches Only:
After reconciliation, If no new terms are proposed, new_terms_proposed must
be an empty array [].

RULE EVOLUTION PERMISSION (EDGE CASES | INCONSISTENCES | CONTRADICTIONS | GAPS)
You are authorized to propose new rules when you encounter an edge case not fully
governed by current rules, when rules are inconsistent or contradictory, or when
gaps in rules allow for unintended data inclusion.

Scope:
Per-record proposals : use when the proposal would positively affect record’s interpretation or validation.
Batch-level proposals: use when the proposal would help avoid unintended recurring patterns across records.

NEW SCHEMA KEY EVOLUTION PERMISSION
You are authorized to propose new schema keys when you encounter data not captured by
or misrepresented in current schema.

Hard constraints:
Do not add new output schema keys, propose them.
Do not change current behavior without updated rules.
Resolve the current run using existing rules and highest-authority precedence.
Treat your proposal as advisory unless explicitly adopted in rulesets or schema.

Where to place proposals:
Record-level: append to _reconciled_notes as [Proposed [Rule|Key]]
Batch-level : append to _reconciled_run_notes as [Proposed [Rule|Key]]

Required Proposal Format (minimum fields):
Trigger: what factual pattern has been identified.
Conflict: which existing rules/keys were insufficient or in tension.
Proposed Rule/Key Text: one concise normative rule or schema key per proposal.
Impact: what this would change in future runs.
Risk if not adopted: concrete failure mode.
Scope: record-level, batch-level, or both
Priority: high, medium, low
Append anything else not cover by minimum fields.

Decision guidance:
If multiple possible proposals exist for the same identified pattern, provide the
narrowest proposal that resolves the issue.
Prioritize proposals that don't require increased researcher or reconciler judgement.

Loophole Guard:
If a any gap is found, do not exploit it for permissive output.
It is required: Produce the safest intended output and add a [Proposed [Rule/Key]] entry.

_RECONCILED_NOTES STANDARD
_reconciled_notes is per-record audit detail.
Use it when any record-level reconciliation action occurs.

Minimum expected content when present:
— any corrected schema violation,
— any corrected data value,
— source choice rationale for conflicts,
— factual field changes and reasons,
— removal reasons for urls, citations, invalid slugs, or companion fields,
— taxonomy selection during reconciliation with reasoning when non—obvious,
— any unresolved gaps requiring reviewer attention.

Omit only when no reconciliation action occurred for that record.

---

_RECONCILED_RUN_NOTES STANDARD
_reconciled_run_notes is batch-level audit detail in meta.

Use it for:
— global policies applied across records,
— web research not available in source materials,
— missing information in available web research ,
— cross-record normalization patterns,
— batch-level reconciler context,
— responses to input prompt queries.

Omit when no batch-level detail is needed.

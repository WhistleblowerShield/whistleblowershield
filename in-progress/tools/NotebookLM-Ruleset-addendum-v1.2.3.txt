WhistleblowerShield.org NotebookLM Ruleset - Addendum v1.2.3

PURPOSE
This addendum carries edge-case and operational policy for NotebookLM
reconciliation. It extends the embedded core ruleset.

AUTHORITY MODEL
- Core embed remains baseline authority.
- Addendum rules refine implementation details.
- Addendum may override core only when explicitly marked as OVERRIDE.

OVERRIDE FORMAT
Use this exact header for any future override:
[OVERRIDE <id>] Replaces core section: <name>

If a rule is not marked as OVERRIDE, treat it as supplemental only.

---

URL POLICY

1) Existing URLs from source records
If URL is already present and domain is approved, carry it forward unless:
- domain is actually unapproved,
- URL pattern is clearly malformed,
- source context indicates fabrication.
Do not drop existing approved-source URLs solely because web search is unavailable.

2) New URLs proposed during reconciliation
Must be verified against a live page on an approved domain before inclusion.
Do not claim internal-memory verification.
If unverifiable, omit the field.
Do not substitute homepage, root, or parent path as fallback.

3) When web search is unavailable
- Keep existing approved-source URLs unchanged.
- Omit newly proposed URLs.
- Log this constraint in _reconciled_run_notes.

ATTACHED CITATION DEDUPE (PARENT-SCOPED)
For citations.attached_citations rows in the same record:

1) Dedupe key
- Use CASE (first token before "||") as the canonical identity.
- CASE matching is case-insensitive and whitespace-insensitive.
- Do not emit duplicate rows for the same CASE within one parent record.

2) Merge rule when IMPACT/URL differ for same CASE
- Keep one row.
- IMPACT: keep the most specific action-verbed statement; if both add distinct facts,
	merge into one concise IMPACT sentence.
- URL: keep one best approved-source URL. If one URL is clearly superior
	(official/authoritative), keep that one.
- SOURCE/QUALITY: keep values aligned to the selected URL/source confidence.

3) Conflict logging
- When duplicate CASE rows were merged because IMPACT or URL disagreed,
	add a note in _reconciled_notes describing the consolidation choice.

4) Prohibited output
- Never output two attached_citations rows for the same CASE under the same
	parent record.

FOR COMMON LAW RECORD TYPES
In record.burden_of_proof:
If statutory_preclusion is set true, statutory_preclusion_details must accompy it,
if the field is empty correct statutory_preclusion to false, and note it in with
error_details. If statutory_preclusion is set to false and statutory_preclusion_details
has text, remove statutory_preclusion_details, and note it with error_details.

Omit when "":
- burden_of_proof.statutory_preclusion_details

---

HAS-DETAILS AS SOLE ARRAY ENTRY
has-details may appear as the only entry in a valid taxonomy array when all
substantive slugs have been removed or moved to new_terms_proposed.

When this occurs:
1) Attempt to populate the companion *_details field from verified statute text.
2) If populated, log the action in _reconciled_notes.
3) If the companion field cannot be populated from verified sources:
	 - preserve ["has-details"],
	 - omit the companion field,
	 - set with_errors: true,
	 - add to error_details exactly:
		 "[STATUTE_ID]: has-details is sole entry in [FIELD] - companion field unresolvable; human review required."

---

CROSS-TAXONOMY MAPPING STRICTNESS
A valid slug must not only exist in registered taxonomy, it must also be
assigned to the exact taxonomy table designated for that schema field.

Do not cross-pollinate slugs across taxonomy arrays.
Examples:
- burden_of_proof.employer_defense accepts only ws_employer_defense slugs
- burden_of_proof.employee_standard accepts only ws_employee_standard slugs

If the assigned table lacks an adequate slug:
1) use has-details where valid and document nuance in the companion *_details,
	 or
2) propose a new term in new_terms_proposed.

Placing a slug into an unassigned array is a schema corruption event and must
be removed, then logged.

---

PROPOSED TERM DISCIPLINE
Invalid or unregistered slugs must not remain in record arrays.
If a concept requires new vocabulary:
1) remove invalid slug from record array,
2) add structured proposal in new_terms_proposed,
3) keep proposal only in proposal list, never in record arrays.

If a slug appears in both record array and new_terms_proposed,
remove it from the record array.

---

BROAD TERM RESOLUTION
Before proposing a broad term:
1) review existing child slugs,
2) use existing child combinations when they remain accurate and specific,
3) propose broader term only when existing combinations misrepresent coverage,
4) document the comparison reasoning in _reconciled_notes.

---

_RECONCILED_NOTES STANDARD
_reconciled_notes is per-record audit detail.
Use it when any record-level reconciliation action occurs.

Minimum expected content when present:
- source choice rationale for conflicts,
- factual field changes and reasons,
- removal reasons for citations/links,
- unresolved gaps requiring reviewer attention,
- taxonomy selection reasoning when non-obvious.

Omit only when no reconciliation action occurred for that record.

---

_RECONCILED_RUN_NOTES STANDARD
_reconciled_run_notes is batch-level audit detail in meta.
Use it for:
- global policies applied across records,
- environment constraints (for example web search unavailable),
- cross-record normalization patterns,
- batch-level reviewer context.

Omit when no batch-level note is needed.

RULE EVOLUTION PERMISSION (EDGE CASES)

You are authorized to propose new rules when you encounter an edge case not fully governed by current rules.

Scope:

Per-record proposals: use when the gap affects one record’s interpretation or validation.
Batch-level proposals: use when the gap reflects a recurring pattern across records.
Hard constraints:

Do not invent new output schema keys.
Do not change current behavior silently.
Resolve the current run using existing rules and highest-authority precedence.
Treat your proposal as advisory unless explicitly adopted by a human.
Where to place proposals:

Record-level: append under _reconciled_notes in a section titled Proposed Rule.
Batch-level: append under _reconciled_run_notes in a section titled Proposed Rule.
Required proposal format (exact fields):

Trigger: what factual pattern caused the gap
Conflict: which existing rules were insufficient or in tension
Proposed Rule Text: one concise normative rule
Impact: what this would change in future runs
Risk if not adopted: concrete failure mode
Scope: record-level, batch-level, or both
Priority: high, medium, low
Decision rule:
If multiple possible proposals exist, provide the narrowest rule that resolves the gap without broadening model discretion.

Loophole Guard:
If a gap is found, do not exploit it for permissive output; produce the safest compliant output and emit a Proposed Rule entry.

2) classify as core or edge,
3) patch addendum first,
4) promote to embed only after repeated confirmation.

Keep addendum lean. Remove superseded entries once promoted to embed.
